# Upac — финальная заметка.

## 1. Корень системы.

Система держится на одном неизменяемом образе на весь `/`, одном overlay для конфигов и одном разделе на запись. Пакеты берутся из одного семейства (одного репозитория одного релиза дистрибутива), поэтому конфликтов между семействами нет по построению.

```
erofs-образ (неизменяемый, корень /):
  /pkg/<пакет>/<id>          указатель: узлы пакета — те же иноды, что в /cmp
  /pkg/<пакет>/triggers      триггеры, объявленные пакетом
  /pkg/upac-tx/              журнал транзакций образа
  /binary  /library          хардлинки на файлы из /cmp — для человека
  /config-defaults           хардлинки на /cmp/usr/etc — умолчания конфигов всех пакетов
  /cmp                       FHS-раскладка для программ, источник правды о метаданных;
                             атрибут user.upac.symlink.hidden — имена, видимые из корня:
                             usr, etc, bin, lib, lib64, sbin
  /cmp/usr/...               FHS-дерево
  /cmp/usr/etc/...           умолчания конфигов: usr/etc пакетов и их etc, перенесённый при импорте
  /cmp/etc                   пустой каталог — точка монтирования /config
  /cmp/bin → usr/bin …       симлинки слитого /usr, как их поставляет дистрибутив
  /state                     пустой каталог — точка монтирования раздела на запись
  /usr → /cmp/usr, /etc → /cmp/etc   невидимые симлинки из user.upac.symlink.hidden [скрыты]
  /bin → /cmp/usr/bin, /lib → /cmp/usr/lib, /lib64 → /cmp/usr/lib64, /sbin → /cmp/usr/bin   [скрыты]

/config = overlay   (redirect_dir=off, metacopy=off)
  lower: /config-defaults                        (из образа, только чтение)
  upper: /state/deploy/<digest>/config/upper     (свой у каждого образа)
  work:  /state/deploy/<digest>/config/work      (служебный, на той же ФС, что upper)

/cmp/etc  = bind /config
```

Неизменяемый образ меняется целиком при перезагрузке. Хардлинки работают, потому что `/pkg`, `/binary`, `/library`, `/config-defaults` и `/cmp` лежат в одном образе.

Человеческие имена (`/binary`, `/library`, `/config`) выбраны так, чтобы не совпадать ни с одним FHS-именем. Тогда `/bin`, `/lib`, `/lib64`, `/sbin` остаются ровно такими, как их поставляет дистрибутив, и внутри одного каталога не приходится смешивать человеческие и FHS-записи. Имена условные.

`/config` — один overlayfs на весь каталог. Чтение: overlay ищет файл сначала в upper, потом в lower. Запись: при первой записи файл из lower копируется в upper (copy-up), образ не трогается. Удаление: в upper появляется whiteout. Временные файлы и `rename` работают, потому что всё внутри одного маунта. Upper — это ровно все правки пользователя и программ и ничего больше. В образ правки не вшиваются, умолчания в нём остаются умолчаниями пакетов — поэтому новое умолчание из обновлённого пакета не сталкивается с правкой пользователя внутри образа. Overlay монтируется с `redirect_dir=off` и `metacopy=off`: тогда в upper лежат только целые файлы, whiteout (символьное устройство `0:0`) и метка непрозрачного каталога `trusted.overlay.opaque`, и upper можно читать как обычное дерево.

Upper у каждого образа свой (раздел 6): образ и его upper — пара. Откат на старый образ возвращает и его конфиг.

Нижний слой `/config` — один слитый каталог, а не `etc` каждого пакета отдельно: у overlay предел нижних слоёв — 500 (константа `OVL_MAX_STACK`), а при многих слоях медленны промахи.

## 2. Пакет.

### 2.1. /pkg — указатель на /cmp.

```
/pkg/<имя>:<архитектура>[:<подархитектура>]/<id>
```

Источник правды о файле — его инод в `/cmp`: содержимое, режим, владелец и xattr (например, `security.capability`). `/pkg` ничего из этого не повторяет — он показывает те же иноды, сгруппированные по пакетам:

- обычный файл и симлинк — узел в `/pkg` и его места в `/cmp` это один и тот же инод (хардлинк). `ls -l` и `getfattr` по пути в `/pkg` показывают ровно то, что видит программа по пути в `/cmp`; разойтись нечему;
- каталог — хардлинк на каталог в VFS невозможен, поэтому узел каталога в `/pkg` — симлинк на его путь в `/cmp`.

Каждый узел — ровно одно место в `/cmp`: место входит в id узла (раздел 2.2), поэтому у инода узла один путь в `/cmp`, и узел однозначно значит «это место этого пакета». Где стоит файл пакета, upac выводит из самого дерева: образ читается целиком одним проходом (или берётся из памяти при сборке нового образа), и за этот проход строится индекс «узел → место». Отдельного списка мест нет — он повторял бы дерево и мог бы с ним разойтись. Вручную то же показывает `find / -samefile /pkg/<пакет>/<id>`.

Имя каталога пакета — `<имя>:<архитектура>`, с `:<подархитектура>`, если она есть. Архитектура входит в ключ: один пакет может стоять для двух архитектур. Символы, которые нельзя или опасно держать в имени каталога (`/`, нулевой байт, `:` внутри компонента), заменяются на `_`. Замена теряет информацию, поэтому два разных пакета могут дать одно имя — это явная ошибка при установке, а не перезапись.

### 2.2. id узла.

```
<тип>-<хеш содержимого>-<хеш метаданных>
```

Оба хеша — хеш verity. Хеш содержимого обычного файла совпадает с хешем его объекта в хранилище composefs (у маленьких файлов, которые лежат прямо в образе, — с хешем, который был бы у такого объекта). Хеш метаданных считается от места узла (путь в дереве образа), права (`режим & 0o7777`), владельца, группы и всех xattr инода в фиксированном порядке; время изменения в него не входит, чтобы одинаковые пакеты, собранные в разное время, давали одинаковые id.

Один узел — одно место и один набор метаданных. Одинаковое содержимое с одинаковыми метаданными в разных местах — разные узлы и разные иноды; то же содержимое с другими правами — тоже другой узел. Объект в хранилище при этом всё равно один. Место в id нужно для владения: хардлинк указывает на инод, а не на путь, и если бы один инод стоял на местах разных пакетов (все пустые файлы `0644 root:root` дают одинаковое содержимое и метаданные), по `/pkg` нельзя было бы понять, какое место чьё. Два пакета с одинаковым файлом на одном и том же месте дают один id и общий узел: место живёт, пока его объявляет хоть один пакет. Каталоги этим правилом пользовались всегда — их содержимое и есть путь.

Типы:

1. `file` — обычный файл. Содержимое — байты файла.
2. `symlink` — симлинк. Содержимое — цель симлинка.
3. `dir` — каталог. Содержимое — путь каталога, поэтому каждый каталог уникален. Описываются все каталоги, включая каталоги со стандартными правами: так сохраняются пустые каталоги и точные права из исходного пакета, а при транзакции видны конфликты, когда два пакета объявляют один каталог с разными правами.
4. Устройства и прочие типы — по тому же принципу, при необходимости: своя метка в id и своё определение содержимого.

### 2.3. Служебные файлы базы.

Метаданные самой базы — пустые обычные файлы, значения лежат в их xattr в пространстве `user.*` (читается всеми, `getfattr` сразу показывает, что это):

- `/pkg/<пакет>/triggers` — триггеры, которые объявил пакет: `user.upac.triggers` — строки `<позиция> <имя>` (`post-install ldconfig`), `user.upac.format` — формат пакета. Нужны, чтобы запустить хуки удаления, когда самого пакета уже нет.
- `/pkg/upac-tx/<время>:<вид>` — журнал транзакций образа, плоский: одна запись — что сделали (`install`, `update`, `uninstall`, `files`, `bootstrap`) и над чем (`user.upac.tx.subject`), с необязательным сообщением (`user.upac.tx.message`). Время — в наносекундах. Журнал растёт с каждой транзакцией, поэтому два образа с одинаковыми файлами всё равно различаются.

Версии, зависимости и описание пакета появятся позже в том же виде — маленький файл с xattr в каталоге пакета.

### 2.4. Файлы пользователя.

Свои файлы в `/usr` пользователь кладёт так: содержимое — в хранилище, место — в `/cmp`, убрать — удалить место, очистить — сборка мусора хранилища. К `/pkg` это отношения не имеет: файл пользователя — это место в `/cmp`, на которое не указывает ни один узел `/pkg`.

## 3. Сборка дерева при транзакции.

Новый образ собирается из предыдущего и импортированных пакетов в одно дерево: `/cmp/usr` — FHS-пути как они есть в пакетах; узлы `/pkg` — хардлинки и симлинки на них; `/binary` и `/library` — те же файлы, отобранные по типам; `/config-defaults` — хардлинки на `/cmp/usr/etc`. Слоёв overlay и пространств имён нет: одно дерево на систему. xattr из пакета (например, `security.capability` из pax-заголовков tar или `RPMTAG_FILECAPS`) переносятся на инод в `/cmp`. Импорт и сборку делает крейт `core/image`.

Пакет приходит в импорт деревом, а не распакованным каталогом. Декодер кладёт содержимое крупных файлов объектами в хранилище и отдаёт дерево пакета в нативной раскладке как dumpfile composefs — текст, где каждая строка — узел: путь, режим, владелец, xattr, цель симлинка или маленькое содержимое, digest объекта, хардлинки. Через границу плагина (C-ABI) идут только байты, поэтому метаданные переносятся точно и без root. Хост разбирает dumpfile в дерево с проверкой и сверяет, что каждый объект, на который оно ссылается, есть в хранилище. Подписывать dumpfile не нужно: он не покидает память процесса, а содержимое объектов защищено их digest и fs-verity; распакованного каталога, который можно подменить между распаковкой и импортом, больше нет.

Умолчания конфигов лежат в одном месте — `/cmp/usr/etc`, для всех пакетов. `etc/...` пакета импорт переносит в `/cmp/usr/etc/...`; `usr/etc/...` пакетов, которые уже кладут умолчания туда (openSUSE, hermetic-usr), ложатся как есть. Совпадение путей обрабатывается как любое другое: одинаковые узлы — один инод, разное содержимое — конфликт (проверка 3), включая пакет, который кладёт и `etc/x`, и `usr/etc/x`; каталоги обязаны совпасть в правах и владельце (проверка 4). `/cmp/etc` в образе пустой: при работе это bind `/config`, а `/config` — overlay с нижним слоем `/config-defaults`.

Симлинк из умолчаний с относительной целью, которая выходит за пределы `etc` (`etc/os-release → ../usr/lib/os-release`), при импорте переписывается в абсолютный путь, вычисленный от его исходного места в пакете (`/usr/lib/os-release`): иначе он разрешался бы по-разному через `/etc` и через `/usr/etc`. Относительные цели внутри `etc` и абсолютные цели не трогаются. Симлинки, которые указывают в `etc` (`/usr/bin/editor → /etc/alternatives/editor`, `/etc/localtime`), продолжают вести в живой `/etc`, а не в `/usr/etc`: ссылка на конфиг должна видеть правки пользователя. Содержимое переписанного симлинка отличается от пакетного, поэтому и id узла другой; два пакета с одинаковым исходным симлинком дают одинаковый переписанный.

Известное следствие: умолчания видны и как `/usr/etc/...` (через `/usr → /cmp/usr`). Программа, которая читает только `/etc`, после удаления `/etc/x` (whiteout в upper) файла не видит; программа на libeconf откатывается на `/usr/etc/x`, то есть удаление для неё — сброс на умолчание. Для пакетов из мира `/usr/etc` так и задумано; для deb и rpm `/usr/etc` появился из-за переноса.

Производные части — `/binary`, `/library`, `/config-defaults`, `/state`, скрытые корневые симлинки и `/.hidden` — выводятся из `/cmp` при каждой сборке и сверяются с тем, что уже лежит в образе: совпадающая запись остаётся, отличающаяся заменяется, лишняя удаляется. Так новая версия upac с изменённой раскладкой этих каталогов не оставляет в образе следов старой.

Типы файлов (программы, библиотеки, интерпретаторы, данные) — это индексы базы `/pkg`, а не слои ФС: «покажи все библиотеки», «какие бинари зависят от `libssl`» — запросы к базе.

Триггеры пакетов (`ldconfig`, кеши иконок, схем, шрифтов) выполняются при сборке над деревом: собранный образ монтируется с временным upper, хуки работают в chroot, их результат накладывается обратно на дерево и попадает в образ. На живой системе не выполняется ничего.

Проверка до коммита — не сошлось хоть что-то, коммита нет:

1. Каждый `DT_NEEDED` закрыт: в дереве есть библиотека с таким soname.
2. У каждого скрипта есть интерпретатор из его шебанга.
3. Нет двух пакетов на один путь с разным содержимым.
4. Каталоги, объявленные разными пакетами, не расходятся в правах и владельце.

## 4. Совместимость с FHS.

Программы ищут файлы по вшитым путям (`/usr/...`, `/etc/...`, `/bin/sh`, `/lib64/ld-linux…`), поэтому FHS-дерево должно отвечать на эти пути. Оно лежит в `/cmp`, а в корне на него указывают невидимые симлинки:

```
open("/usr/lib/foo.so")
  → / : запись usr — симлинк на /cmp/usr (скрыт из листинга, но поиском находится)
  → /cmp/usr → lib → foo.so → тот же инод, что /pkg/foo:x86_64/file-<хеш>-<хеш>
  → данные из объекта в хранилище, ядро проверяет verity
```

Невидимый симлинк — симлинк, который находится поиском по пути, но не виден в листинге. Источник правды — атрибут `user.upac.symlink.hidden` на `/cmp`: список имён, которые видны из корня (сколько угодно). Ядро следует симлинку по цели и приходит в настоящий каталог `/cmp/usr`, поэтому дентри у каталога один: `..` из него — `/cmp`, `getcwd` и `realpath` возвращают `/cmp/usr/...`. Под `/cmp/usr` лежит полное FHS-дерево, так что программы, которые вычисляют свой префикс от пути к бинарю, не промахиваются: Python из `/cmp/usr/bin/python3` найдёт `/cmp/usr/lib/python3.12`. `/etc` — невидимый симлинк на `/cmp/etc`, а `/cmp/etc` — bind-маунт `/config`; это единственный bind в схеме.

Основа (вариант 1): upac при сборке образа по атрибуту `user.upac.symlink.hidden` кладёт в корень настоящие симлинки (`usr → /cmp/usr` и так далее) с флагом «скрыт» — от ядра нужен только патч скрытия. Целевая идея (вариант 2): в корне нет никаких записей; при промахе поиска в `/` erofs сам читает атрибут `/cmp` и на лету создаёт симлинк-инод с нужной целью. Листинг чист без флагов, но это новый механизм в `erofs_lookup()`: синтетические иноды, их номера, кеш.

Отвергнуто: каталог `/usr` как жёсткая ссылка на тот же инод, что `/cmp/usr`, и перенаправление каталогов через `trusted.overlay.redirect` или запасной поиск в overlay — во всех трёх случаях один каталог оказывается под двумя путями (у composefs нет верхнего слоя, и overlay склеивает иноды по нижнему), а у каталога в VFS может быть только один дентри: ядро переносит его между родителями, и `getcwd` и `..` ведут себя непредсказуемо. Симлинк этим не страдает: он ведёт в настоящий каталог, а не притворяется им. Bind-маунт `/cmp/usr` на скрытый `/usr` тоже работает (`realpath` показывал бы `/usr/...`), но требует точку монтирования в корне. Второе дерево каталогов в образе (хардлинки файлов) работает без маунтов, но дублирует каталоги.

## 5. Скрытие из листинга.

Невидимые симлинки в корне (`usr`, `etc`, `bin`, `lib`, `lib64`, `sbin`) скрыты из листинга, но находятся поиском по пути: человек видит `ls /` без них, программа открывает `/usr/...` как обычно.

На стоковом ядре — файл `/.hidden` со списком имён. Его читают GIO (Nautilus, диалоги GTK, порталы) и KIO (Dolphin); ядро о нём не знает, `ls` в терминале покажет всё.

С патчем erofs — флаг в записи каталога. Запись выглядит так:

```c
struct erofs_dirent {
	__le64 nid;      /* номер узла */
	__le16 nameoff;  /* смещение имени */
	__u8 file_type;
	__u8 reserved;   /* сейчас не используется */
} __packed;
```

Один бит в `reserved` — флаг «скрыт»; при сборке образа upac ставит его на нужные записи. Писатель erofs в composefs-rs сейчас всегда пишет `reserved = 0`, поэтому для флага нужен патч писателя (или свой писатель образа). Патч ядра — несколько строк в `erofs_fill_dentries()` (`fs/erofs/dir.c`), перед `dir_emit()`:

```c
#define EROFS_DIRENT_HIDDEN 0x01

if (de->reserved & EROFS_DIRENT_HIDDEN) {
	++de;
	ctx->pos += sizeof(struct erofs_dirent);
	continue;
}
```

`readdir` пропускает запись: её не видят `ls`, `ls -a`, файловые менеджеры, автодополнение. `lookup` (`fs/erofs/namei.c`) ищет имя бинарным поиском и на `reserved` не смотрит: `open`, `cd /usr`, `ls /usr` работают. Позиция каталога сдвигается и для скрытых записей, поэтому `telldir`/`seekdir` не ломаются. Через overlay composefs работает: overlay берёт листинг у erofs. Стоковое ядро байт `reserved` не проверяет и на том же образе просто покажет скрытые записи — некрасиво, но ничего не сломается.

Опционально — запрет `cd` в скрытые каталоги верхнего уровня через BPF LSM: `chdir`, `fchdir` и `chroot` передают в проверку прав флаг `MAY_CHDIR` (`fs/open.c`), хук `inode_permission` может отказать. Без патча ядра, если BPF LSM включён (`bpf` в `lsm=`). Глубже запрещать нельзя: программы законно листают `/usr/share/icons`, `/usr/share/fonts`, каталоги модулей Python. Это забор, а не замок: точный путь работает и обязан работать — так файлы открывают программы.

## 6. Раздел на запись, деплои и загрузка.

Корень `/` — образ из хранилища, а само хранилище и всё изменяемое лежат на отдельном физическом разделе. Чтобы upac мог записать новый образ или правку конфига, раздел виден внутри системы как `/state` — обратная ссылка на тот раздел, из которого собран корень. Для всей системы `/state` смонтирован только для чтения; upac перемонтирует его на запись в своём пространстве имён монтирования, остальные процессы писать в него не могут.

```
/state/composefs/                       хранилище: объекты и образы
/state/deploy/<digest>/                 деплой — пара «образ + его конфиг»
    config/upper  config/work           upper и work overlay /config этого образа
    history/<время>                     снимки upper: digest снимка и сообщение в xattr
    pinned                              пустой файл: образ закреплён
/state/deploy/current → <digest>        симлинк на текущий образ
```

Все записи о состоянии — файлы с xattr, записанные атомарно: временный файл, xattr, переименование. `current` меняется так же: новый симлинк под временным именем переименовывается поверх старого.

**Переключение образа.** Пусть R — образ, с которого запущена система, а T — образ, на который переключаемся (откат или новый образ после установки; у нового образа upper пустой). Новый upper T — это upper R, наложенный поверх старого upper T по правилам overlayfs (whiteout удаляет, непрозрачный каталог заменяет), и всё это сплющивается в один upper — цепочка слоёв не растёт. Своего слияния содержимого нет: файл, который правил пользователь, перекрывает умолчание, нетронутый файл просвечивает из нового `/config-defaults`. Upper T сохраняется снимком до и после сплющивания, так что переключение обратимо. Сплющивание происходит в момент команды; правки, сделанные между командой и перезагрузкой, не переносятся. Для путей из upper R, у которых умолчание в R и T разное, upac выводит предупреждение: правка пользователя перекрывает новое умолчание, а само новое умолчание видно в `/config-defaults`.

**`upac commit`** сохраняет upper текущего образа как образ в хранилище и добавляет запись в его `history/`.

**Загрузка.** Неделимая единица загрузки — запись загрузчика: UKI (ядро, initramfs и командная строка с `composefs=<digest>` в одном подписанном файле) или BLS-запись с ядром и initramfs. Ядро, initramfs и образ в ней не могут разойтись. Запись собирается из образа по его digest и публикуется на ESP атомарно; порядок: опубликовать запись → поставить её загрузчику → переставить `current`. Initramfs монтирует образ по `composefs=<digest>` из командной строки своей записи — так работают откат из меню загрузчика и цепочка доверия Secure Boot. Если загрузился не `current` (выбран другой пункт меню или сбой между шагами), initramfs переставляет `current` на то, что реально загрузилось.

## 7. Открытые вопросы.

| Вопрос | Суть |
|---|---|
| Декодеры | переход на выдачу dumpfile; ни один декодер пока не переносит xattr (`security.capability` и прочие) |
| Метаданные пакета | версии, зависимости, их разрешение — формат файла в `/pkg/<пакет>/` |
| Сборка записи загрузчика | отдельный крейт: сборка BLS/UKI из образа, публикация на ESP |
| Форк setup-root | монтирование образа, `/state`, `/config`, сверка `current` при загрузке |
| `/var`, `/home` | раскладка вне образа не описана |
| `fsck.erofs` | не ругается ли erofs-utils на ненулевой `reserved` |
| `/usr` и `/etc` как симлинки | проверить на раннем старте (systemd и PAM читают `/etc` очень рано) и на программах, которые сравнивают реальный путь с вшитым `/usr/...` |
| Вариант 2 | невидимые симлинки без записей в корне: синтез симлинк-инодов в `erofs_lookup()` по атрибуту `/cmp` |
| Запрет `cd` | эксперимент с BPF LSM: что из софта на нём ломается (`find /usr`, `updatedb`, бэкапы) |

## 8. Вне основы.

Смешивание пакетов разных семейств, изоляция программ (свои корни, слои, пространства имён) и человеческая раскладка сверх `/binary` и `/library` из основы вынесены. Их можно надстроить позже над той же базой `/pkg`, ничего не перепроектируя.
